## 协议卡

### 执行流程

\```text
前置
  □ 创建 Cursor Rule（一次性）
  □ G  冒烟测试 + 骨架扫描

代码流
  □ C1  <文件>  <FR>
  □ C2  <文件>  <FR>
  ...                          ← 无依赖且不共享文件的批次标注 ∥ 可并行

Prompt 审查（如适用）
  □ P1  审查 Prompt vs SPEC    <FR>
  □ P2  补缺（如有）

集成验收
  □ F1  自动化：全量测试 + NFR + 假设
  □ S   Spec 回写（如有 🟡 积累）
  □ F-manual  E2E 端到端    <FR>

回顾（可选）
  □ R   执行回顾
\```

### 完成标准

- [ ] 全量 unit test 通过
- [ ] lint + format 通过
- [ ] 每个 FR 每条 AC: ✅ 或 ⚠️有记录
- [ ] NFR 验证方法已执行
- [ ] Prompt 审查完成（如适用）
- [ ] ≥1 个 E2E 场景验证通过
- [ ] IMPL-PROGRESS.md 全部 ✅ 或有明确记录

### 批次内部节奏

每张批次卡已将四步显式内联（①②③④），Agent 无需参照此处。此节仅供人了解方法论。

**棕地**：① 审计（读源文件+测试→对照AC填表）→ ② 判断 → ③ 补缺（先测试→再实现）→ ④ 质量门
**绿地**：① 规划（读SPEC/IMPL→列实现方案+测试断言）→ ② 判断（🟡保守实现/🔴暂停）→ ③ 先写测试骨架→再实现 → ④ 质量门

C 批次默认 Agent 模式。若 ① 审计发现 >6 AC 有缺口，可先用 Ask 模式完成审计，再切 Agent 模式执行 ③。

### 快速通道

当一个批次审计全 ✅ **且仅有 ≤ 3 行非功能性修改**（如 docstring、type hint 补充）且质量门通过，可在同一对话中直接继续下一批次。

### 跨批次变更协议

| 场景 | 处理 |
|------|------|
| 小调整（≤ 5 行，不改接口） | 当前批次中修改，质量门改为全量回归 |
| 需改接口签名 | 暂停 → 回上游批次重新审计 → 更新 IMPL-PROGRESS.md |
| 发现上游遗漏 AC | 记录 🟡 → Phase S，或在当前批次补充 |

### 版本控制

- 每个批次通过质量门后 commit
- 遵循项目已有的 commit 规范；FR 引用放入 commit body
- 若项目无 commit 规范，使用: `<type>(<scope>): <一句话描述>`
  body 中标注: `Batch: Cx | FR: FR-xx, FR-yy`
- 类型: feat / fix / refactor / test / docs / chore
- 不要在批次中间 commit 未通过质量门的代码
- 每个批次质量门 ④.7 必须输出本次修改对应的 git commit message 建议（标题 + 正文 `Batch/FR` 备注），供用户直接执行 `git commit`；Agent 不自行执行 commit，除非用户显式要求

#### Commit message 生成规则

| 维度 | 规则 |
|------|------|
| `<type>` | 按本批次修改性质选一：`feat`（新功能）/ `fix`（修缺陷）/ `refactor`（重构无行为变化）/ `test`（仅测试）/ `docs`（SKILL.md / spec 回写 / README）/ `chore`（依赖 / 构建 / 配置 / 骨架） |
| `<scope>` | 使用项目固定 scope（见项目约定；无固定则取主模块名） |
| `<摘要>` | 小写祈使句，≤ 72 字符，反映本批次核心产出（专有名词除外） |
| 正文首行 | `Batch: <批次号> \| FR: <FR 列表，逗号分隔；无 FR 则写 —>` |
| 正文后续 | 可选：变更文件要点（仅当质量门 ④.0 涉及多文件跨域时） |
| 多 FR | FR 列表**只列**本批次卡头部 `FR:` 行所述的 FR 编号（去重、去 AC 明细） |

### Spec 反馈分类

- **🔴 阻塞**：AC 歧义到无法判断实现对错 → 暂停，修 spec
- **🟡 非阻塞**：措辞不精确但方向明确 → 记录，Phase S 处理
```

### R2：上下文管理

### R3：失败恢复

| 故障 | 恢复 |
|------|------|
| 旧测试断言不完整 | 更新旧测试匹配新的正确行为 |
| 新代码破坏正确行为 | `git checkout -- {file}` → 兼容重做 |
| 🔴 spec 矛盾 | 暂停 → 修 spec → 回步骤 ① |
| Cursor 违反约束 | 新对话，"批次 Cx 步骤 N" |
| ≥3 轮修不好 | 🔴 blocked → 跳过 → 最后处理 |

### R4：Spec 反馈判断

| 类型 | 标准 | 处理 |
|------|------|------|
| 🔴 阻塞 | AC 歧义到无法判断对错 | 立即修 |
| 🟡 非阻塞 | 不精确但方向明确 | Phase S |
| 不更新 | 内部实现细节 | 不动 |

### R5：AC 验证类型

| 类型 | 含义 | 示例 |
|------|------|------|
| 单测 | pytest 断言 | 确定性算法 |

## 执行期协议

执行批次过程中按需查阅的协议。SKILL.md 中的生成流程不依赖此章节。

### 增量更新协议

当 SPEC.md 在 Playbook 生成后被更新（Changelog 有新条目）：

1. **识别变更范围** — 读 SPEC Changelog，提取受影响的 FR/NFR 编号
2. **重新映射** — 仅对变更的 FR 重新执行第三步（FR → 文件映射）
3. **更新批次** —
   - FR 仍在原批次范围 → 更新该批次卡的 AC 表
   - FR 需要新批次 → 在依赖链中插入新批次卡（编号 Cx.1）
   - FR 已删除 → 移除对应 AC 行，空批次整体删除
4. **标注** — 在受影响批次卡顶部标注 `🔄 更新于 <date>：<变更摘要>`
5. **更新索引** — 同步更新 FR → 批次索引表

未完成的批次直接更新；已完成的批次标注 `⚠️ 需重新审计`（从 ① 重新开始）。

**示例：** SPEC 新增 FR-16（依赖 FR-01），归属 C1 的源文件：
- C1 已完成 → C1 卡顶部加 `⚠️ 需重新审计`，AC 表追加 FR-16 行
- 索引表追加 `FR-16 | C1 | 单测 | @t/sandbox`
- 执行流程 checklist 的 C1 行恢复为 □
- IMPL-PROGRESS.md 中 C1 状态改为 🔧，备注"FR-16 新增"
