# Spec → Playbook

读取 spec 目录，生成三份产物：
1. **IMPL-PLAYBOOK.md** — 面向 Cursor Agent 的分批执行手册
2. **IMPL-PROGRESS.md** — 跨会话执行进度追踪（独立小文件，Agent 可靠编辑）
3. **.cursor/rules/<topic>.mdc** — 自动注入的编码约束

## 输入

spec 目录路径。若未指定，搜索 `specs/*/SPEC.md` 模式自动定位。
最低要求 SPEC.md 存在；有 DESIGN.md 和 IMPL-GUIDE.md 时输出质量更高。

## TL;DR 决策树

```text
读 Spec → 就绪性检查 → 扫描代码库 → FR→文件映射(含置信度) → 批次计划 → 计划评审 → 生成产物 → 分级自检(CRITICAL/WARNING/SUGGESTION)
```

核心逻辑：**FR 按文件亲和分组 → 依赖链排序 → 每批次 ≤ 10 AC + ≤ 1500 行上下文**。
绿地先写测试骨架后实现，棕地先审计后补缺。每批次四步：① 读 → ② 判 → ③ 做 → ④ 门。
PLAYBOOK 只读参考，PROGRESS 独立小文件供 Agent 可靠编辑和断点续传。

## ⚡ 核心规则（每次必读）

以下 16 条是生成和自检的硬约束。详细流程和边缘场景在后续章节展开，但这些规则**始终优先**。

**映射与分组：**
1. 每条 FR 必须映射到实际源文件后才能分配批次（不空映）
2. FR→文件映射标注置信度（🟢/🟡/🔴），🔴 低置信度在计划评审中高亮待确认
3. 同文件的 FR 归同批次（文件亲和）；依赖链决定批次顺序
4. 单批次 ≤ 10 AC + ≤ 1500 行上下文；超限则拆分或缩小读取范围

**批次卡：**
5. 每张 C 批次卡必须自包含 ①②③④ 四步，粘贴即可用
6. 每张卡必须有 ⛔ 范围行，列出允许修改的文件
7. 棕地 ③ = 先补测试→再补实现；绿地 ③ = 先写测试骨架→再实现
8. 批次卡 ① 中 `@` 引用使用完整路径（非别名）

**质量门：**
9. ④.0 范围验证：`git diff --name-only` 确认修改在 ⛔ 内（机械验证，非自律）
10. ④.1 修改了非本批次首创的文件 → 全量回归测试
11. ④.5 前向检查：声明下游批次依赖的接口
12. ④.7 提交信息：输出本次修改对应的 git commit message 建议（Conventional Commits + `Batch: <批次号> \| FR: <FR 列表或 —>` 正文），Agent 不自动执行 `git commit`

**自检（分级）：**
13. CRITICAL #2,#3,#5,#13 必须全过；WARNING #4,#7,#8,#14,#15,#16 标注后可交付；SUGGESTION #1,#6,#9-#12 建议修复
14. 语义抽查不确定时降级为 WARNING（非 CRITICAL），每个不通过项必须附具体修复建议

**护栏：**
15. 不编造 spec 中不存在的 FR/AC/NFR
16. 手册是指令，不是理论——给出具体步骤，不解释方法论

> 后续章节是核心规则的**展开和细化**。遇到冲突时，以核心规则为准。

## 工作流程

### 第一步：读取 Spec

读取所有可用 spec 文件，提取结构化信息：

| 来源 | 提取内容 |
|------|---------|
| SPEC.md | FR（含 AC、优先级、依赖图）、NFR（含验证方法）、IR、假设、E2E 场景、术语表 |
| DESIGN.md | ADR、架构组件、Agent 设计（如适用）、错误处理策略 |
| IMPL-GUIDE.md | Tool 协议、数据模型、项目结构、测试策略、环境变量、AI Coding Agent Prompt |

若 IMPL-GUIDE 有 "AI Coding Agent Prompt" 章节，用作 Cursor Rule 的基础素材。

### 第一步半：Spec 就绪性检查

在映射 FR 之前，验证 spec 输入质量。逐条扫描并报告：

| 检查项 | 不通过处理 |
|--------|-----------|
| 每条 FR 是否有 ≥1 条 AC | ⚠️ 标注 `FR-xx: 缺少 AC — 无法生成审计表` |
| 每条 NFR 是否有验证方法 | ⚠️ 标注 `NFR-xx: 缺少验证方法` |
| FR > 8 条时是否有依赖图 | ⚠️ 标注 `FR 依赖图缺失 — 批次排序可能不准确` |
| FR AC 中是否含实现绑定（函数名/变量名） | ⚠️ 标注具体 AC，但不阻断 |

- 有 ⚠️ → 在 PLAYBOOK 开头"Spec 就绪性"区列出所有警告
- 无 ⚠️ → 跳过该区

此步不阻断生成，但确保用户知晓 spec 中的质量缺口。

### 第二步：扫描代码库

判断项目状态：
- **绿地**（仅脚手架）→ 手册侧重"从零实现"
- **棕地**（已有实质代码）→ 手册侧重"审计 + 补缺"

映射实际目录：
- 源文件 → 函数/类（按文件统计，不逐行精读）+ **大致行数**
- 测试文件 → 对应源文件 + **大致行数**
- 入口文件（agent.py / main.py / app.py 等）
- 已有 Cursor Rule（.cursor/rules/）
- Prompt 文件（若为 Agent 系统）
- 无 FR 映射的源文件 → 标注 `ℹ️ orphan — 不在 spec 范围内`

记录文件行数用于第四步的上下文预算控制。

### 第三步：FR → 文件 + 验证类型映射

为每条 FR 确定：
- **主源文件** — 核心逻辑所在
- **测试文件** — 覆盖它的测试
- **验证类型** — 按下表分类
- **依赖** — 来自 SPEC.md FR 依赖图
- **映射置信度** — 按下表分级

**映射置信度：**

| 级别 | 判定标准 | 处理 |
|------|---------|------|
| 🟢 高 | 文件中已扫描到与 FR 关键词直接对应的函数/类 | 正常流转 |
| 🟡 中 | 文件名/模块名暗示相关，但未精读确认含目标逻辑 | 在计划评审中标注，建议用户确认 |
| 🔴 低 | 基于推断或排除法，无直接证据 | 计划评审中**必须高亮**，用户未确认则不生成该批次卡 |

低置信度映射在计划评审表（第四步半）中以 `⚠️` 前缀标注。

**FR 验证类型分类表：**

| 信号 | 类型 |
|------|------|
| 无代码实现，仅 System Prompt 约束 | Prompt 行为 |
| 确定性算法，I/O 可测 | 单测 |
| 需外部服务（沙箱、API、DB） | 集成测试 |
| 配置项 / 环境变量 | 配置审查 |
| "所有代码路径都须满足 X" | 代码审查 |
| 同时有代码和 Prompt 组件 | 拆分：代码部分→单测，Prompt 部分→Prompt 行为 |
| Prompt 约束但可通过代码守卫兜底 | Prompt 行为 + 代码守卫（如配额硬计数器、措辞正则校验、强制超时） |

### 第四步：生成批次计划

按**文件亲和**分组（同文件的 FR 归同批次），再按**依赖链**排序。

分组规则：
1. 每批次涉及 ≤ 2-3 个源文件
2. 共享主源文件的 FR 归入同一批次
3. 依赖顺序：FR-A 依赖 FR-B → B 的批次排在前面
4. 单文件 FR > 6 条 → 按关注点拆子批次
5. 跨批次 FR：归入主验证所在批次，标注跨切性质
6. 纯 Prompt FR → 独立 Prompt 流（P1..Pn）
7. 需运行时/人工验证 FR → 手动流（F-manual）
8. **AC 上限**：单批次 ≤ 10 条 AC；超过时按关注点拆分
9. **上下文预算**：单批次引用文件总行数 ≤ 1500 行；超过时在 ① 中改为"读 `@file` 中与 FR-xx 相关的函数/类"而非整个文件
10. **并行标识**：无直接依赖、不共享源文件、不共享测试文件（含 fixture/conftest）、不共享结构文件（`__init__.py`、数据模型）、且无前向依赖引用（④.5 未互相提及）的批次标注 `∥ 可并行`，在执行流程 checklist 中缩进对齐显示

**流命名约定：**

| 流 | 编号 | 说明 |
|----|------|------|
| 前置 | G | 全局冒烟测试 + 骨架扫描 |
| 代码流 | C1, C2, ... Cn | 可自动测试的 FR |
| Prompt 流 | P1, P2 | Prompt 行为审查 + 补缺 |
| 集成验收 | F1, F2, F-manual | 自动化 / 人工辅助 / 纯手动 |
| Spec 回写 | S | 集中处理 🟡 积累（F1 后、F-manual 前） |
| 回顾 | R | 执行回顾（可选） |

**非 Agent 项目适配：**
- 无 Agent/LLM 组件 → 跳过 P1/P2 流和 F-manual 中 Prompt 验证表
- 无 E2E 场景 → F-manual 可省略，在 F1 中增加集成测试覆盖
- 完成标准相应缩减：仅保留 G → C → F1 → S → R

### 第四步半：计划评审

批次计划生成后、写入 PLAYBOOK 前，输出精简评审摘要供用户确认：

```text
## 批次计划评审

项目状态：绿地 / 棕地 / 混合
FR 总数：X | 批次总数：Y（C: a, P: b, F: c）

| 批次 | FR | 主文件 | AC 数 | 上下文行数 | 置信度 | 依赖 |
|------|----|--------|------|-----------|--------|------|
| C1 | FR-01 | src/foo.py | 4 | ~320 | 🟢 | — |
| C2 | FR-02, FR-10 | src/bar.py | 7 | ~680 | 🟢 | C1 |
| ⚠️ C3 | FR-05 | src/baz.py | 3 | ~150 | 🔴 低 | C1 |
...

∥ 可并行组：{C3, C4}
🔴 低置信度映射：{列出所有 🔴 映射，需用户确认后才生成对应批次卡}

风险提示：
- {如有：某批次 AC 数接近上限、跨切批次多、依赖链深等}

确认后继续生成完整 PLAYBOOK，或指出需要调整的批次。
```

用户确认（或调整）后继续。若用户无响应，默认通过。

### 第五步：生成 IMPL-PLAYBOOK.md

输出到 `<spec-dir>/IMPL-PLAYBOOK.md`。完整模板见 [reference.md](reference.md)。

结构概览：

```text
1. 元数据头（status / version / date / skill_version）
2. 使用方法（2-3 行）
3. Spec 就绪性警告（如有）
4. 路径约定（cwd + 别名映射表 + @ 引用说明）
5. FR → 批次索引表
6. 协议卡
   ├── 执行流程 checklist
   ├── 完成标准
   ├── 批次内部节奏（审计→判断→补缺→质量门）
   ├── 快速通道
   ├── 跨批次变更协议
   ├── 版本控制协议
   └── Spec 反馈分类
7. 环境准备（Cursor Rule 内容内联）
8. 批次卡（每批一张，可直接粘贴到 Cursor Agent）
9. 执行进度引用（指向 IMPL-PROGRESS.md）
10. 参考区（R1-R6 模板）
```

### 第六步：生成 Cursor Rule

输出到 `.cursor/rules/<topic>.mdc`。

内容来源：
- 项目描述 → SPEC.md Quick Context
- 硬约束 → DESIGN.md ADR + IMPL-GUIDE 约束
- 测试/lint 命令 → IMPL-GUIDE 测试策略

≤ 25 行。只纳入"违反就会写错代码"的约束。

```text
---
description: <一句话项目描述> constraints
globs: <项目 glob 模式>
---

<一句话用途>。Spec 在 <spec_dir>/。

硬约束：
{从 ADR 和 IMPL-GUIDE 提取}

验证：{测试 + lint 命令}
```

## 批次卡结构
<!-- 展开核心规则 #5-#8 -->

每张批次卡 = 一段可直接粘贴到 Cursor Agent 的完整指令。四个步骤全部显式写出
（Agent 无需参照协议卡即可执行）。

**路径引用规则：**
- 路径约定表**必须声明工作目录**（`cwd`），质量门中所有命令基于此目录执行
- 批次卡 ① 中的 `@` 引用**必须使用完整路径**（非别名），确保粘贴即可用
- 别名仅用于执行流程 checklist 和 FR→批次索引表（概览场景），文档头部**必须提供完整的别名→路径映射表**
- 别名表与 Cursor `@` 引用兼容

**棕地批次卡模板：**

```text
### Cx：<标题>

批次 Cx：<标题>
FR: <FR 列表+AC 编号> | NFR: <关联 NFR> | IR/假设: <引用>
注意: <跨批次、仅 Prompt、拆分等，无则省略>
⛔ 范围：仅修改上述源文件和测试文件；不得修改其他文件除非 AC 明确要求。不得预先实现后续批次的功能。

① 读以下文件当前版本，对照 SPEC 审计每条 AC：
- @<源文件路径>
- @<测试文件路径>
- @<spec_dir>/SPEC.md（搜索 `### FR-xx:`）

逐条填写审计结果：

| AC | 摘要 | 代码 | 测试 | 备注 |
|----|------|------|------|------|
| FR-xx AC-y | <一句话，来自 SPEC> | | | <非单测则标注验证类型> |
...

② 全 ✅ → 跳到 ④。有缺口 → 继续 ③。

③ 补缺：先补测试 → 再补实现 → 运行测试确认通过。
   测试连续失败 ≥3 次 → 停止修复，在 IMPL-PROGRESS.md 标注 `❌ 阻塞: <失败信息>`，跳到下一个无依赖批次。

④ 质量门：
0. 范围：`git diff --name-only` 确认修改文件均在 ⛔ 列表内；有越界文件 → 撤回越界修改后再继续
1. 回归：<具体 pytest 命令>
   - 若本批次修改了非本批次首创的文件 → 改为全量回归测试
2. Lint：<具体 ruff/lint 命令>
3. 验收：本批次每条 AC → ✅/❌
4. Spec 反馈：🔴/🟡/无
5. 前向：<下一批次依赖本批次的什么接口>
6. 进度：更新 <spec-dir>/IMPL-PROGRESS.md
7. 提交信息：按"版本控制"章节规则输出本次修改的 git commit message 建议，格式为 `<type>(<scope>): <摘要>` + 空行 + `Batch: Cx | FR: <本批次 FR 列表；无则写 —>`；`<type>` 按本批变更性质选 `feat`/`fix`/`refactor`/`test`/`docs`/`chore`；Agent 不自动执行 `git commit`
```

**绿地批次卡模板：**

```text
### Cx：<标题>

批次 Cx：<标题>
FR: <FR 列表+AC 编号> | NFR: <关联 NFR> | IR/假设: <引用>

⛔ 范围：仅创建/修改上述源文件和测试文件；不得修改其他文件除非 AC 明确要求。不得预先实现后续批次的功能。

① 读 @<spec_dir>/SPEC.md（搜索 `### FR-xx:`）+ @<spec_dir>/IMPL-GUIDE.md 相关章节，
  规划实现方案。若源文件已有脚手架则一并读取。

列出实现计划：

| AC | 摘要 | 测试断言 | 实现方案 | 备注 |
|----|------|---------|---------|------|
| FR-xx AC-y | <一句话，来自 SPEC> | <预期断言> | <计划> | <非单测则标注验证类型> |

   测试连续失败 ≥3 次 → 停止修复，在 IMPL-PROGRESS.md 标注 `❌ 阻塞: <失败信息>`，跳到下一个无依赖批次。

④ 质量门：
0. 范围：`git diff --name-only` 确认修改文件均在 ⛔ 列表内；有越界文件 → 撤回越界修改后再继续
1. 回归：<具体 pytest 命令>
   - 若本批次修改了非本批次首创的文件 → 改为全量回归测试
2. Lint：<具体 ruff/lint 命令>
3. 验收：本批次每条 AC → ✅/❌
4. Spec 反馈：🔴/🟡/无
5. 前向：<下一批次依赖本批次的什么接口>
6. 进度：更新 <spec-dir>/IMPL-PROGRESS.md
7. 提交信息：按"版本控制"章节规则输出本次修改的 git commit message 建议，格式为 `<type>(<scope>): <摘要>` + 空行 + `Batch: Cx | FR: <本批次 FR 列表；无则写 —>`；`<type>` 按本批变更性质选 `feat`/`fix`/`refactor`/`test`/`docs`/`chore`；Agent 不自动执行 `git commit`
```

关键规则：
- **自包含** — 卡片可独立粘贴，Agent 无需参照协议卡或参考区
- **四步显式** — ①②③④ 全部写出，绿地/棕地使用对应模板
- **范围围栏** — 每张卡显式标注 ⛔ 范围，防止 Agent 越界修改。⛔ 中的文件路径基于 cwd（与 ① 的 `@` 全路径引用区分：⛔ 描述约束，① 引用文件内容）。质量门 ④.0 通过 `git diff --name-only` 机械验证围栏合规
- **跨切接口摘要** — 标注"跨 Cx"的批次，在 ① 之前增加"前置接口"段，用 1-2 行列出每个跨切依赖的函数签名和预期行为（从前置批次的 ④.5 前向检查提取）。确保 Agent 无需回读上游批次源文件即可完成审计
- AC 摘要直接从 SPEC.md 浓缩为一短语
- 代码/测试列留空——执行时由 Agent 填写
- 备注列标注非标准验证类型（代码审查、集成测试、Prompt 行为等）
- 前向检查：明确下游批次对本批次的接口依赖
- **跨批次回归**：修改了上游批次文件 → 质量门升级为全量测试
- **共享文件必全量**：当连续批次共享 ⛔ 范围中的源文件或测试文件时（如按关注点拆分的子批次），后续批次的质量门 ④.1 直接写全量回归命令（不加 "若" 条件），因为共享文件场景下条件必然为真
- **提交信息建议**：④.7 要求 Agent 在质量门通过后输出 commit message 建议（标题 + `Batch/FR` 正文）；Agent **不得自动执行** `git commit`，由用户决定何时提交。每张 C 批次卡的 ④.7 需预填本批次号（`Batch: Cx`）和本批次 FR 列表（来自卡头 `FR:` 行，去重、去 AC 明细，无则写 `—`）
- **模式选择**：C 批次默认 Agent 模式。若 ① 审计发现 >6 AC 有缺口，可先用 Ask 模式完成审计，再切 Agent 模式执行 ③

## 执行状态追踪
<!-- 按需查阅：生成 PROGRESS 文件时参照 -->

## 生成后自检
<!-- 展开核心规则 #12-#13 -->

PLAYBOOK 输出完成后，按优先级逐条验证。交付规则：有 CRITICAL → 必须修复；仅 WARNING → 标注后可交付；仅 SUGGESTION → 直接交付。

**验证启发式：**
- 结构检查（#1-#12）：客观、二元判定，无歧义
- 语义抽查（#13-#15）：允许不确定性，不确定时降级为 WARNING 而非 CRITICAL
- 不确定时的分级倾向：WARNING > CRITICAL，标注 > 沉默
- 每个不通过项必须附具体修复建议（含文件路径/批次编号），不接受"请检查"式模糊建议

**CRITICAL（必须修复才能交付）：**

| # | 检查项 | 验证方式 |

| 2 | 每张批次卡含 ⛔ 范围行 | 搜索 `⛔` |

| 13 | FR→文件映射语义抽查 | 抽查 2 个 FR→文件映射：读对应源文件，确认含与该 FR 直接相关的函数/类/逻辑 |

**WARNING（应当修复）：**

| # | 检查项 | 验证方式 |

## 护栏
<!-- 展开核心规则 #14-#15 -->

- **不编造** — 不创造 spec 中不存在的 FR/AC/NFR
- **不空映** — 必须检查实际源文件后才将 FR 分配到批次
- **标未知** — FR 无法映射到源文件 → 标注 `📝 unmapped — needs discussion`
- **降级输出** — 按以下阶梯降级，每级在 PLAYBOOK "Spec 就绪性"区标注跳过的检查及原因：

  | 可用输入 | 生成内容 | 跳过内容 | 自检缩减 |
  |---------|---------|---------|---------|
  | SPEC only | 批次卡（无 ADR 约束）+ 简化 Rule（仅项目描述+测试命令） | Cursor Rule 中 ADR 硬约束；F1 Coherence 中 ADR 验证；P1 中设计一致性 | #14 依赖链抽查降级为 SUGGESTION |
  | SPEC + DESIGN | 批次卡 + 完整 Rule | F1 Coherence.c 代码模式检查中 IMPL-GUIDE 协议引用 | 完整自检 |
  | SPEC + DESIGN + IMPL-GUIDE | 完整三件套 | 无 | 完整自检 |
- **验证 glob** — Cursor Rule 的 glob 必须匹配实际项目目录
- **无 Agent 无 Prompt 流** — 系统不含 Agent → 跳过 P1/P2
- **手册是指令，不是理论** — 给出具体步骤，不解释方法论
- **语言匹配** — 手册语言匹配 spec 文档语言；FR/AC/NFR/ADR 等技术缩写保持英文
- **上下文可控** — 单批次引用文件总行数 > 1500 行时缩小读取范围
- **绿地/棕地一致** — 批次卡 ③ 均为测试优先（绿地先写测试骨架再实现，棕地先补测试再补实现）
- **大型项目拆分** — FR > 25 → 建议按模块/子系统拆分为多个独立 PLAYBOOK，每个 ≤ 15 FR
