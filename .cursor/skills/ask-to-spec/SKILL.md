# Ask → Spec

将本轮 Ask 模式对话收敛为生产级系统文档集。

角色定位：**系统架构专家**（根据系统类型动态补充领域专长，如 Agent 系统、安全工程、数据工程等）。

输出三份独立文档，职责分明：

```
specs/<topic>/
├── SPEC.md        # 需求（What + Why + 约束）
├── DESIGN.md      # 架构设计（How）
└── IMPL-GUIDE.md  # 实现指引（Build）
```

---

## 工作流程

### 第一步：识别系统轮廓 + 回溯对话

在写任何内容之前，先完成三件事：

**A) 系统轮廓识别** — 判断系统类型并确定章节侧重：

| 系统类型 | DESIGN 侧重 | IMPL-GUIDE 侧重 | 可裁剪章节 |
|----------|-------------|------------------|-----------|
| Agent 系统 | Agent 能力表、推理流程、状态管理 | Tool 协议、Prompt 模板 | — |
| API 服务 | 接口契约、服务拓扑 | Endpoint schema、错误码 | Agent 设计（裁剪或简化） |
| 数据管道 | DAG 编排、数据血缘 | 调度配置、Schema 定义 | Agent 设计、Prompt 模板 |
| SDK / Library | 公共 API 设计、扩展点 | 类型定义、使用示例 | Agent 设计、Prompt 模板 |
| 前端应用 | 组件架构、状态管理、路由 | 组件树、Store 定义、样式系统 | Agent 设计、Prompt 模板 |
| CLI 工具 | 子命令树、参数解析、TUI 架构 | 参数 schema、输出格式 | Agent 设计、Prompt 模板 |
| 混合系统 | 按主要组件组合上述侧重 | 按主要组件组合 | 各类型可裁剪章节取并集 |

**混合系统**先识别核心组件类型（如 "Agent 系统 + API 服务"），然后合并两种类型的侧重项。上表未覆盖的系统类型（如微服务、移动端、ML Pipeline、基础设施即代码等），根据其核心能力自行选定侧重，不适用的章节标注 N/A。

如果系统不含 Agent 组件，DESIGN.md 的 "Agent 设计" 章节标注 `N/A — 本系统不包含 Agent 组件` 而非强行填写。

**B) 绿地 vs 存量判断：**

若对话涉及已有系统的改进（非绿地项目），额外标记：
- SPEC 中已有能力标注 `✅ 已实现`，新增需求正常编写
- DESIGN 中标注 `🔧 需重构` 或 `🆕 新增` 以区分组件状态
- IMPL-GUIDE 中标注当前代码路径和变更范围

若为全新系统则跳过此步。

**C) 回溯对话，提取决策：**

1. **最终方案** — 仅保留经过讨论后确认的方案，丢弃中间探索
2. **关键决策** — 每个选择的 why（不只是 what）
3. **假设与不确定项** — 用 `⚠️ 假设:` 和 `❓ 待定:` 标记
4. **隐性需求** — 对话中暗示但未明确提出的需求
5. **矛盾 / 未解决冲突** — 对话中前后不一致或悬而未决的分歧

**D) 确定输出范围：**

根据对话深度决定本次输出哪些文档：

| 对话覆盖的层次 | 输出文档 |
|----------------|---------|
| 仅讨论了需求（做什么/为什么） | 仅 SPEC.md |
| 需求 + 架构讨论（怎么做） | SPEC.md + DESIGN.md |
| 完整覆盖需求/架构/实现 | 全部三份 |

用户可显式要求 `spec only` / `spec + design` / `full set` 覆盖此推断。未输出的文档在已输出文档的末尾标注 `📝 后续文档：DESIGN.md / IMPL-GUIDE.md 待进一步讨论后生成`。

### 第二步：提取摘要，用户确认

将提取结果**展示实际内容**（非仅计数）呈现给用户：

```
📋 决策提取摘要
━━━━━━━━━━━━━━━
系统类型：<type>
项目性质：绿地 / 存量改进
输出范围：SPEC / SPEC + DESIGN / 全部三份

**最终方案（N 条）：**
1. <方案一句话描述>
2. ...

**假设（N 条）：**
⚠️ <假设内容>
...

**待定（N 条）：**
❓ <待定内容>
...

**矛盾 / 未解决冲突（N 条）：**
⚡ <对话中 X 处说了 A，但 Y 处倾向 B。请确认>
...

**隐性需求（N 条）：**
1. <隐性需求> — 推理依据：...
...
```

用户确认后再进入正式撰写。如用户有修正，先更新提取结果。**矛盾项必须在用户确认阶段解决**，不得带入文档生成。

**快速通道：** 当同时满足以下条件时，可将摘要内联到 SPEC.md 开头（跳过独立确认步骤）：FR ≤ 5 且无矛盾项且待定项 ≤ 1（已标注的假设不阻断快速通道）。

### 第三步：依次生成文档

按顺序生成，后一份依赖前一份的内容：

| 顺序 | 文件 | 模板 | 核心问题 | 变更门槛 |
|------|------|------|----------|----------|
| 1 | `SPEC.md` | [templates/SPEC.md](templates/SPEC.md) | 做什么、为什么、约束 | 需求评审 |
| 2 | `DESIGN.md` | [templates/DESIGN.md](templates/DESIGN.md) | 怎么做、架构选型 | 设计评审 |
| 3 | `IMPL-GUIDE.md` | [templates/IMPL-GUIDE.md](templates/IMPL-GUIDE.md) | 具体 schema / prompt / 指令 | 随开发迭代 |

**大型系统分步输出：** 当满足以下任一条件时建议分批输出——先输出 SPEC.md 待用户确认需求无误，再输出 DESIGN.md 待用户确认架构，最后输出 IMPL-GUIDE.md。每份文档独立输出，减少单次生成的 token 压力和截断风险。

- FR 数量 > 10 **或** FR 中有 ≥ 3 个包含状态机/循环的需求
- Tool 数量 > 5 **或** Agent 推理流程步骤 > 8
- 预估单份文档 > 200 行

**超大文档拆分策略：** 当单份文档 > 500 行时，可按以下方式拆分：

| 文档 | 拆分方式 | 索引方式 |
|------|---------|---------|
| IMPL-GUIDE.md | 拆为索引 + `IMPL-GUIDE-tools.md`（Tool 协议）+ `IMPL-GUIDE-prompts.md`（Prompt 模板） | 索引文件用 `→ 详见 IMPL-GUIDE-tools.md` 引用 |
| SPEC.md | 极少需要拆分；若 FR > 20，可按功能域拆为 `SPEC-core.md` + `SPEC-extended.md` | 索引文件保留 Quick Context / 范围 / 术语表 |
| DESIGN.md | 优先精简而非拆分；若确实过长，按架构层拆分 | 每份保留关键设计决策章节 |

**文档间引用规则：**
- `DESIGN.md` 每个设计决策必须引用 `SPEC.md` 中具体的 FR/NFR 编号（如 `> 来源：FR-01, FR-03`），禁止笼统引用（如 `FR-01 ~ FR-15 综合`）
- `IMPL-GUIDE.md` 必须引用 `DESIGN.md` 中的架构组件来说明实现对象

**关键原则：**

- **语言**：匹配对话主要语言（对话为中文则中文输出，英文则英文输出），技术术语保留英文原词。模板中的中文章节标题和注释应随输出语言同步切换
- **需求强度词**：英文输出时使用 RFC 2119 关键词（MUST / SHOULD / MAY）区分强制程度；中文输出时对应使用「必须 / 应当 / 可以」
- **Changelog 日期格式**：统一使用 ISO 8601（`YYYY-MM-DD`）
- **版本里程碑**：`v1.0` = 首次通过需求/设计评审的版本；此前为 `v0.x` 草稿迭代
- 每个章节必须有实质内容；**对话未涉及的章节**标注 `📝 待补充：需进一步讨论` 而非强行填充
- DESIGN 和 IMPL-GUIDE 中的草稿必须是可执行级别，不是描述性散文
- 若系统包含 Agent 组件，Agent 设计是重中之重，必须建模完整
- **US 覆盖粒度**：单个 US 覆盖的 FR 不应超过总 FR 数的 60%，否则应拆分为更聚焦的子场景

**回退协议：** 生成过程中发现以下情况，立即回退到前序文档补充：
- 写 DESIGN 时发现 SPEC 缺少必要的 FR/NFR → 暂停，补充 SPEC 后继续
- 写 IMPL-GUIDE 时发现 DESIGN 缺少组件 → 暂停，补充 DESIGN 后继续
- 回退时在变更处标注 `🔄 回退补充`，Changelog 记录触发原因

**生成过程中的边界防线（写时检查）：**

规则详见各模板中的内联注释。核心原则：

- **SPEC**：验收标准描述**可观测的系统行为**，不引用内部函数/类/变量名，不嵌入实现参数
  - **自检问句 1**：如果把所有函数/变量重命名，这条验收标准是否仍然成立？
  - **自检问句 2**：这个数字是业务约定还是实现选择？（判定指引见下方）
- **DESIGN**：描述组件角色和交互关系，具体 JSON schema / Prompt 文本留给 IMPL-GUIDE
- **IMPL-GUIDE**：发现新需求回写 SPEC，不在此文档中引入

**业务约定 vs 实现选择判定指引：**

验收标准中出现具体数字时，按以下规则判定：

| 来源 | 分类 | 处理方式 |
|------|------|---------|
| 业务方/产品经理明确拍板（"用户每月最多免费分析 10 次"） | 业务约定 | 留在 SPEC 验收标准中 |
| 工程侧权衡（"5 步足够覆盖典型场景"） | 实现选择 | 移到 IMPL-GUIDE，SPEC 只说"系统限制单次操作次数" |
| 对话中未明确来源 | 默认为实现选择 | SPEC 中用 `（默认值见 IMPL-GUIDE）` 引用 |
| 涉及外部合同/SLA/法规（"GDPR 要求 72 小时内通知"） | 业务约定 | 留在 SPEC，标注来源 |

### 第四步：质量自检

分两步执行：先运行强制扫描（机械检查），再逐条过质量检查清单。

**4a) 强制扫描（必须逐条执行，输出扫描结果）：**

对已生成的文档执行以下模式扫描，发现违规则修复后再继续：

| 扫描目标 | 扫描模式 | 违规处理 |
|----------|---------|---------|
| SPEC 验收标准含实现绑定 | 搜索反引号包裹的蛇形命名（`` `\w+_\w+` ``）、`stdout`、`stderr`、`exit_code`、`return code`、具体函数/类名 | 重写为可观测行为描述 |
| SPEC 验收标准含无来源数字 | 搜索 `\d+`，逐条判定：业务约定→保留，实现选择/来源不明→改为「系统限制…（默认值见 IMPL-GUIDE）」 | 移至 IMPL-GUIDE 或标注来源 |
| SPEC 验收标准含接口协议细节 | 搜索「标准输出」「错误输出」「退出码」「HTTP 状态码 xxx」「JSON 字段名」等具体协议词 | 抽象为「命令执行结果」「错误信息」「执行状态」等 |
| DESIGN 状态管理泄露实现 | 搜索括号补充说明（`（.*?）`），检查是否含数据结构类型（字典/列表/数组等）、变量名、模块路径 | 移除实现细节，仅保留存储语义 |
| DESIGN 含范围式引用 | 搜索 `~` 字符 | 改为逐条列举具体 FR/NFR 编号 |
| 引用完整性 | DESIGN 每个 `> 来源:` 中的编号在 SPEC 中存在；IMPL-GUIDE 每个 `> 对应 DESIGN.md:` / `> 能力:` 在 DESIGN 中存在 | 补充缺失引用或修正编号 |
| FR/US 双向一致 | 每条 FR 的 `关联场景:` 非空；每个 US 的 `覆盖 FR:` 与关联 FR 双向一致 | 补全缺失的双向索引 |
| IR 关联完整 | 每条 IR 的 `关联 FR:` 非空 | 补全关联 |
| 假设闭环 | 每条 `⚠️ 假设:` 在 SPEC 假设表中有对应条目且回退方案非空 | 补全假设表 |

**4b) 质量检查清单** — 逐条过检，修复不达标项。

### 第五步：输出文件

保存至 `specs/<topic>/`，其中 `<topic>` 为 kebab-case 主题名。
如对话涉及明确项目名则用项目名，否则从对话主题推导。

**增量更新：** 如果目标目录已存在，先读取现有内容，然后：
1. 仅更新/补充本轮对话涉及的章节
2. 在变更处标注 `🔄 本轮更新`
3. 在文档头部 `## Changelog` 追加一条变更记录（日期 + 一句话摘要）

**增量更新冲突处理：**
- 新决策与现有内容矛盾时，**标注 `⚡ 冲突：` 并附两版内容**，由用户裁决
- 用户裁决后更新内容并在 Changelog 记录 `resolve conflict: ...`
- `🔄 本轮更新` 标记在**下一次版本号升级时移除**

**级联更新规则：**
- SPEC 变更 → 检查并更新引用了该 FR/NFR 的所有 DESIGN 决策和 IMPL-GUIDE 实现项
- DESIGN 变更 → 检查并更新引用了该组件的 IMPL-GUIDE 实现项
- IMPL-GUIDE 变更 → 如果发现了新需求，回写 SPEC（不在 IMPL-GUIDE 中引入）

**用户反馈迭代协议：**

当用户在文档输出后提出修改意见时：

| 反馈对象 | 处理流程 |
|----------|---------|
| 对 SPEC 有修改 | 更新 SPEC → 按级联规则检查 DESIGN/IMPL-GUIDE 中引用了变更 FR/NFR 的所有章节 |
| 对 DESIGN 有修改 | 更新 DESIGN → 检查是否需要回写 SPEC（新需求/新约束）→ 级联检查 IMPL-GUIDE |
| 对 IMPL-GUIDE 有修改 | 更新 IMPL-GUIDE → 若涉及新需求则回写 SPEC |

- 变更范围 > 3 个 FR 时，建议重新走第二步「摘要确认」，防止理解偏差积累
- 每次反馈迭代后重新执行第四步「质量自检」中的强制扫描

## 各文档撰写指南

### SPEC.md — 需求层（What）

纯粹定义系统**要做什么**和**约束条件**。绝不包含"怎么做"。

- **元数据头** — status / version / date（模板自带）
- **Quick Context** — 一句话，5 秒理解
- **术语表** — 领域术语统一定义，确保三份文档用词一致
- **背景与目标** — 为什么做 + 可度量成功标准
- **范围** — In Scope / Out of Scope
- **用户场景** — 2-3 个用户故事（`作为 <角色>，我想 <行为>，以便 <价值>`），每个标注 `覆盖 FR:` 反向索引
- **端到端验收场景** — 将用户故事展开为跨 FR 的完整路径，标注 `来源 US:` + 涉及的 FR 和预期终态（含异常路径）
- **FR 依赖关系图** — 当 FR > 8 条时，用 Mermaid 图展示 FR 间依赖关系
- **功能需求（FR）** — 使用**卡片式格式**（见模板），每条包含：
  - 编号 + 优先级（P0/P1/P2，见模板中定义） + 依赖
  - 一段描述（系统**能力**，不绑定实现）
  - 拆条的验收标准（每条描述可观测行为，不引用函数名/类名/变量名/实现参数）
  - **自检**：重命名所有函数后验收标准是否仍成立？数字是业务约定还是实现选择？
- **非功能需求（NFR）** — 具体可度量指标 + **验证方法**，不是模糊描述（"高性能"/"低延迟" 不合格）
  - 类别按系统类型动态选取（见模板注释），不强制填满预设类别
- **隐性需求** — 每条标注推理依据和关联 FR
- **假设** — 对话中未被验证的前提条件，每条标注验证方式、回退方案和关联 FR/NFR。散落在其他章节中的 `⚠️ 假设:` 标注必须在假设表中有对应条目
- **风险** — 影响 / 概率 / 缓解措施 / Owner / 监控指标

### DESIGN.md — 设计层（How）

描述**架构方案**，每个设计决策必须追溯到 SPEC.md 中的**具体**需求编号。

- **关键设计决策** — ADR 风格，支持两种格式：
  - **表格格式**：适用于 1-2 行理由即可说清楚的简单决策
  - **展开格式**：适用于权衡涉及多个维度的复杂决策（上下文 / 方案对比 / 结论 / 后果）
- **Agent 设计**（仅 Agent 系统，否则标注 N/A）
  - Agent 能力表（职责 / 输入 / 输出 / 需要的能力，不绑定具体 Tool）
  - Agent 间协作（仅多 Agent 系统：通信协议 / 委托规则 / 冲突解决）
  - 推理流程（编号步骤 + 流程图，标注决策点 / 循环 / 退出条件）
  - 状态管理（上下文维护、存储语义、恢复机制——描述"存在哪里"的语义而非变量名）
- **安全设计**（当系统处理用户输入、外部调用或隔离执行时）
  - 信任边界（受信 vs 非受信区域）
  - 威胁模型（推荐 STRIDE 框架：Spoofing / Tampering / Repudiation / Info Disclosure / DoS / Elevation；非安全关键系统可简化为关键攻击面分析）
  - 输入验证策略（各层的验证职责）
- **系统架构** — 按需裁剪分层 + 架构图（优先 Mermaid，ASCII 备选）
- **错误处理策略** — 全局错误分类、重试策略、降级策略、熔断机制
- **可观测性设计**（条件见模板注释）— 关键指标、日志策略、分布式追踪
- **外部依赖** — LLM provider / 向量库 / 外部 API / 沙箱（含 SLA / 限流 / 成本）
- **迁移策略**（仅存量系统）— 当前状态 → 目标状态的迁移路径，标注里程碑和回滚点
- **数据流** — 架构级流转图（5-10 步高层流转，不是伪代码），标注各层间数据结构变换。优先 Mermaid sequence diagram，ASCII 备选

**Mermaid 图类型选择指南：**

| 场景 | 推荐图类型 | Mermaid 关键字 |
|------|-----------|---------------|
| FR 依赖关系 | 有向图 | `flowchart LR` |
| 推理流程 / 状态机 | 流程图 | `flowchart TD` |
| 数据流 / 交互时序 | 时序图 | `sequenceDiagram` |
| 信任边界 | 子图流程图 | `flowchart` + `subgraph` |

## 护栏

以下为**生成过程中的行为准则**（区别于上方质量检查清单对产物的验证标准）：

- **不编造** — 对话中没有讨论的内容，不在文档中凭空添加功能
- **宁缺毋滥** — 对话不足以支撑某章节时，标注 `📝 待补充：需进一步讨论`
- **标记推断** — 基于经验补充的内容必须用 `⚠️ 假设:` 标注
- **不遗漏** — 对话中明确确认的决策必须全部体现
- **安全优先** — 涉及用户输入、外部调用、沙箱的地方必须有安全设计
- **立即回退** — 发现前序文档缺口时不强行前进，回退补充后再继续

**合理推断边界：**

| 场景 | 是否允许推断 | 处理方式 |
|------|-------------|---------|
| 对话有明确方向暗示但缺具体参数（如"需要高可用"但未给 SLA） | 允许 | `⚠️ 假设: SLA 99.9%（业界常见值）`，标注在 NFR 和假设表中 |
| 对话未提及但属于该类系统的通用最佳实践（如 API 服务必须有鉴权） | 允许 | 作为 IR（隐性需求）写入 SPEC，标注推理依据 |
| 对话提及技术偏好但未充分论证（如"用 Redis"） | 允许 | 写入 DESIGN ADR，标注 `⚠️ 假设: 对话倾向 Redis，待确认` |
| 对话定性描述性能（如"要快"）但未给量化指标 | 允许 | 推断业界常见值写入 NFR + 假设表，如 `⚠️ 假设: P99 < 200ms` |
| 存量系统未讨论向后兼容 | 允许 | 作为 IR 写入：`向后兼容现有 API/数据格式`，标注推理依据 |
| 对话未提及且属于可选增强（如国际化、暗色模式） | 禁止 | 不写入任何文档 |
| 对话中有分歧但偏向某方（如 70% 讨论倾向方案 A） | 禁止假定 | 列为矛盾项，第二步由用户裁决 |
